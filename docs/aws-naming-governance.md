# PetClinic 클라우드 표준 (STD-CLD-001 · rev 0.2)

Seoul 리전 단일 VPC 위에 Edge · WEB · WAS · DB 4개 계층으로 구성된 PetClinic 3-Tier 아키텍처의 리소스 네이밍 규칙, 태그 거버넌스, 네트워크·보안·비용·운영 정책을 정의한다. 아키텍처 다이어그램(`aws-3tier-arch.png`)에 그려진 모든 구성요소가 적용 대상이다.

| 항목 | 내용 |
| --- | --- |
| 적용 범위 | ap-northeast-2 · 단일 계정 · 단일 환경 |
| 구축 방식 | AWS 콘솔 수동 |
| 작성 | 설동화 (B파트 · WEB Tier) |
| 기준일 | 2026-09-14 |
| 상태 | rev 0.2 |

rev 0.1의 미확정 항목에 대한 팀 결정 결과다. 본문 전체가 이 결정을 전제로 작성되었다.

| ID | 결정 | 내용 |
| --- | --- | --- |
| D1 | 시스템 약어 `ptc` · 환경 토큰 없음 | 네이밍 문법에서 `env`를 제거한다. 단일 환경 단일 계정 운영이므로 이름에 환경을 넣지 않는다. |
| D2 | 단일 계정 · 팀장이 IAM 사용자 발급 | 루트 계정은 팀장이 보유하고, 팀원은 개인 IAM 사용자로 접근한다. |
| D3 | IaC 미사용 — AWS 콘솔 수동 구축 | 네이밍·태그를 강제할 코드가 없으므로 **§14의 사람 절차가 유일한 통제 수단**이다. |
| D4 | 도메인 구매 예정 · HTTPS 구성 예정 | ACM 인증서 2장(서울·버지니아)과 리다이렉트 설계를 §9에 정리. |
| D5 | 로드밸런서는 외부·내부 모두 ALB | NLB 옵션 폐기. Internal LB 이름은 `ptc-alb-int`로 확정. |
| D6 | NAT Gateway를 AZ마다 배치 | AZ 장애 시 아웃바운드 단절 리스크 해소. 대신 최대 비용 항목이 되므로 §13에서 예산을 다룬다. |
| D7 | 팀원 전원 동일 권한 | 권한으로 사고를 막을 수 없는 구조이므로, 사후 추적(CloudTrail)과 삭제 방지 장치로 방어선을 옮긴다(§8.3). |

## §1. 변수 정의

이 문서의 모든 예시는 아래 변수를 조합해 생성된다. 값이 바뀌면 이 표만 고치고 나머지는 따라온다.

| 변수 | 값 | 설명 | 비고 |
| --- | --- | --- | --- |
| `sys` | `ptc` | 시스템 식별자 (PetClinic) | 모든 리소스명의 첫 토큰. 3자 고정 |
| `reg` | `apne2` | 리전 축약 (ap-northeast-2) | 전역 유일 네임스페이스(S3)에만 포함. 버지니아 리소스는 `use1` |
| `rsc` | §3 약어 사전 | 리소스 타입 약어 + 역할 | 사전에 없는 약어는 임의 생성 금지 (§14.4) |
| `az` | `a` · `c` | 가용영역 문자 | 다이어그램상 AZ-a / AZ-c 2개 |
| `nn` | `01` · `02` … | 2자리 일련번호 | 1자리 금지 — 10번을 넘기면 정렬이 깨진다 |

### 1.1 계층 어휘

다이어그램의 박스를 6개 계층으로 정규화한다. 태그·SG·서브넷·로그 그룹이 전부 이 어휘를 공유한다.

| 계층 | 포함 리소스 | 위치 |
| --- | --- | --- |
| `edge` | Route 53, CloudFront, ACM, S3(assets) | 리전 외부 / 글로벌 |
| `net` | VPC, IGW, NAT GW, EIP, 라우트 테이블, VPC Endpoint, 외부 ALB | public-subnet-a / c |
| `web` | Apache EC2(WEB01/02), ASG, 외부 ALB 타겟그룹 | WEB-subnet-a / c (private) |
| `was` | Tomcat EC2(WAS01/02), ASG, Internal ALB, 그 타겟그룹 | WAS-subnet-a / c (private) |
| `db` | RDS MySQL Multi-AZ, 서브넷 그룹, 파라미터 그룹 | DB-subnet-a / c (private) |
| `ops` | CloudWatch, SNS, SSM, IAM, 로그 버킷 | 계정 전역 |

> **Internal ALB의 계층 귀속** — WAS 앞단에 붙으므로 **was 계층**으로 분류한다. 네트워크 장비라고 `net`에 넣으면 "WAS 장애 조사 시 `Tier=was`로 필터" 같은 운영 동작이 깨진다. LB는 자기가 보호하는 티어에 귀속시키는 것이 원칙이며, 외부 ALB만 인터넷 경계 장비라 예외적으로 `net`이다.

## §2. 네이밍 문법

모든 리소스명은 단일 문법을 따른다. 소문자·하이픈 구분이며 왼쪽에서 오른쪽으로 넓은 범위 → 좁은 범위 순서다.

```
sys - (reg) - rsc - (az)(nn)
```

| 토큰 | 필수 여부 |
| --- | --- |
| `sys` · `rsc` | 필수 |
| `reg` | 전역 유일 네임스페이스일 때만 |
| `az` | AZ 종속 리소스일 때만 |
| `nn` | 동일 역할이 2개 이상일 때만 |

> **2.0 — rsc 토큰이 역할까지 담는다**
> 확정된 문법에는 역할(role) 토큰이 따로 없다. 그런데 `ptc-sbn-a`만으로는 WEB·WAS·DB 서브넷을 구분할 수 없다. 따라서 **`rsc`를 "타입-역할" 복합 토큰으로 해석**한다 — `sbn-web`, `tg-was`, `role-ec2-web`처럼 타입 약어 뒤에 역할을 잇는다. 문법의 형태는 그대로 두고 `rsc`의 정의만 넓힌 것이며, 허용 조합은 §3 표가 전부다.

| ID | 규칙 |
| --- | --- |
| N-01 | **소문자와 하이픈(-)만** 쓴다. 대문자·언더스코어·공백·한글·마침표 금지. S3·RDS·ALB는 애초에 언더스코어를 받지 않고, 혼용하면 검색·스크립트 매칭이 전부 깨진다. |
| N-02 | 토큰 순서는 **고정**이다. `ptc-sg-web`은 되고 `sg-ptc-web`은 안 된다 — 콘솔 목록이 `ptc`로 시작해 한 덩어리로 정렬되어야 한다. |
| N-03 | **az와 nn은 붙여 쓴다**: `ptc-ec2-web-a01`. 하이픈으로 또 나누면 토큰이 늘어 32자 제한에 불리하고, 다이어그램의 `WEB01` 표기와도 멀어진다. |
| N-04 | AZ 문자는 **물리 AZ ID가 아니라 논리 AZ 문자**(a/c)를 쓴다. `apne2-az1` 매핑은 계정마다 달라 이름에 박으면 안 된다. |
| N-05 | 이름에 **날짜·리소스 ID·개인 이름**을 넣지 않는다. 예외는 스냅샷과 AMI뿐이며 형식은 `-YYYYMMDD`다. |
| N-06 | `test` · `tmp` · `new` · `final` · `copy` · `2` 같은 **임시 접미는 영구 금지**. 임시 리소스는 이름이 아니라 `ExpireAt` 태그로 구분한다. |
| N-07 | AWS 예약 접두 `aws-` · `amazon-` · `internal-`로 **시작하지 않는다**. 특히 ALB 이름은 `internal-`로 시작할 수 없다. |
| N-08 | 환경 토큰이 없으므로 **이름만으로는 실습용과 제출용을 구분할 수 없다.** 나중에 dev 환경을 만들면 이름이 충돌하니, 그때는 별도 VPC가 아니라 **별도 계정**을 쓰거나 문법에 `env`를 되살려야 한다 (§15-Q1). |

### 2.1 적용 예시

```
ptc-vpc                         ← 전역 단일. az·nn 불필요
ptc-sbn-web-a                   ← WEB-subnet-a (rsc = sbn-web)
ptc-tg-was-8080                 ← 포트를 붙여 타겟그룹 중복 방지
ptc-ec2-web-a01                 ← 다이어그램의 WEB01 + AZ 정보
ptc-ngw-a / ptc-ngw-c           ← AZ별 NAT (D6)
ptc-apne2-assets-123456789012   ← S3: reg + 계정ID로 전역 유일성 확보
/ptc/web/internal-lb-dns        ← SSM 파라미터는 하이픈 대신 슬래시 계층
```

## §3. 리소스별 표준명

다이어그램에 그려진 구성요소 전부의 확정 명칭이다. 콘솔에서 리소스를 만들 때 **표준명 칸을 그대로 복사**해 붙여넣는다. 표에 없는 리소스는 §14.4 절차를 따른다.

| VPC | `vpc` | `ptc-vpc` | 계정당 1개 |

## §4. AWS 제약과 금지 문자

네이밍 규칙보다 상위에 있는 것은 AWS API의 물리적 제약이다. 규칙이 제약과 충돌하면 제약이 이긴다.

| 리소스 | 길이 | 허용 문자 | 걸리기 쉬운 함정 |
| --- | --- | --- | --- |
| ALB 이름 | 1–32 | 영숫자 · 하이픈 | 하이픈 시작/끝 불가 · `internal-` 접두 불가 · **언더스코어 불가** |
| 타겟 그룹 | 1–32 | 영숫자 · 하이픈 | 동일. 삭제 직후 같은 이름 재생성에 지연이 있다 |
| S3 버킷 | 3–63 | 소문자 · 숫자 · 하이픈 · 점 | **전역 유일** · 점을 쓰면 가상호스팅 TLS가 깨짐 → 점 금지 |
| RDS DB 식별자 | 1–63 | 영문자 시작 · 영숫자 · 하이픈 | **언더스코어 불가** · 하이픈 연속 불가 · 하이픈으로 끝날 수 없음 |
| DB 서브넷/파라미터 그룹 | 1–255 | 소문자 · 숫자 · 하이픈 | 대문자를 넣으면 자동 소문자화되어 기록과 실제가 어긋난다 |
| 보안 그룹 이름 | 1–255 | 영숫자 `._-:/()#,@[]+=&;{}!$*` | `sg-`로 **시작 불가** · VPC 내 중복 불가 · **생성 후 변경 불가** |
| IAM 역할 | 1–64 | 영숫자 `+=,.@-_` | 64자는 생각보다 빨리 찬다 |
| IAM 정책 | 1–128 | 동일 | 경로는 길이에 미포함 |
| KMS 별칭 | 1–256 | `alias/` + 영숫자 `/_-` | `alias/aws/`는 AWS 예약 |
| CloudWatch 알람 | 1–255 | ASCII | 계정+리전 내 유일 · 이름 변경 = 삭제 후 재생성 |
| 로그 그룹 | 1–512 | 영숫자 `_-/.#` | 슬래시 계층 권장 · 공백 불가 |
| SSM 파라미터 | 1–1011 | 영숫자 `_-./` | `aws`/`ssm` 접두 예약 · 계층 15단계 제한 |
| EC2 Name 태그 | 1–256 | 유니코드 | 제약이 느슨해 **규칙이 가장 먼저 무너지는 지점** |

> **32자 예산 — env 토큰을 뺀 덕에 여유가 생겼다**
> 가장 긴 이름이 `ptc-tg-was-8080` 15자, `ptc-alb-ext` 11자로 제한의 절반도 쓰지 않는다. 나중에 `env`를 되살리더라도(§15-Q1) 4자(`-dev`)를 더해 19자이므로 문제없다. 지금 짧게 지은 이름이 나중의 확장 여지다.

## §5. 태그 거버넌스

이름은 사람이 읽고 태그는 기계가 읽는다. 콘솔 수동 구축이라 태그를 자동 주입해 줄 코드가 없으므로, **태그는 리소스를 만드는 화면에서 그 자리에 직접 입력**한다. 나중에 몰아서 달면 반드시 빠진다.

### 5.1 필수 태그

태그를 지원하는 모든 리소스에 6개를 부착한다. 환경 토큰이 없어졌으므로 `Env`는 제외했고, 대신 **누가 만들었는지를 남기는 두 개(`Owner`·`Part`)가 핵심**이다.

| 키 | 허용 값 | 용도 |
| --- | --- | --- |
| `Name` | §3 표준명과 동일 | 콘솔 식별 — 리소스명과 반드시 같아야 한다 |
| `System` | `petclinic` | 타 실습 리소스와 구분 · 비용 집계 단위 |
| `Tier` | `edge`\|`net`\|`web`\|`was`\|`db`\|`ops` | 장애 범위 필터 · SG 감사 · 비용 분해 |
| `Part` | `a` \| `b` \| `c` … | 담당 파트. **전원 동일 권한이라 이것이 유일한 소유 표시다** |
| `Owner` | IAM 사용자명 (`seol-donghwa`) | 문의·삭제 승인 대상 |
| `CreatedAt` | `YYYY-MM-DD` | 방치 리소스 판별 · 과제 종료 시 회수 기준 |

### 5.2 조건부 태그

| 키 | 값 | 적용 조건 |
| --- | --- | --- |
| `Backup` | `daily` \| `none` | EBS·RDS 필수 |
| `Schedule` | `always-on` \| `office-hours` | EC2 필수 — §13.2 야간 정지 대상 선별 |
| `ExpireAt` | `YYYY-MM-DD` | 테스트 리소스 필수. 경과 시 회수 |
| `DataClass` | `public` \| `internal` \| `confidential` | S3·RDS — 암호화·공개 설정 수준 결정 |
| `AppVersion` | war 버전 / 커밋 SHA | WEB·WAS 인스턴스 — 배포 추적 |

### 5.3 태그 작성 규칙

| ID | 규칙 |
| --- | --- |
| T-01 | 태그 **키는 PascalCase**(`CreatedAt`), **값은 소문자 kebab**(`seol-donghwa`). AWS 태그 키는 대소문자를 구분하므로 `owner`와 `Owner`는 **서로 다른 태그**다 — 혼용하면 비용 리포트가 둘로 쪼개진다. |
| T-02 | `aws:` 접두는 예약이라 직접 만들 수 없다. |
| T-03 | ASG에 태그를 넣을 때 **"새 인스턴스에 태그 지정(propagate at launch)" 체크박스를 반드시 켠다.** 빠뜨리면 스케일아웃으로 뜬 인스턴스만 태그가 비어 비용 집계와 소유자 추적에서 사라진다 — 콘솔 구축에서 가장 흔한 누락이다. |
| T-04 | 누락분은 **Resource Groups & Tag Editor**에서 리전 전체를 조회해 일괄 부여한다. 주 1회 점검 (§14.3). |
| T-05 | Billing 콘솔에서 `System`·`Tier`·`Part`를 **비용 할당 태그로 활성화**한다. 활성화 시점 이후 데이터만 집계되므로 **구축 첫날에 해야 한다.** |
| T-06 | CloudFront·Route 53 레코드처럼 태그가 지원되지 않거나 전파되지 않는 리소스는 **§14.2 생성 대장**으로만 추적한다. |

## §6. 네트워크·CIDR 할당 정책

서브넷 CIDR은 선착순이 아니라 사전 할당표를 따른다. 여러 사람이 동시에 콘솔에서 서브넷을 만들면 대역이 겹치거나 파편화되기 쉽다.

### 6.1 CIDR 할당표

| 구간 | CIDR | 가용 IP | AZ | 용도 |
| --- | --- | --- | --- | --- |
| VPC | `10.0.0.0/16` | 65,536 | — | 계정 내 유일 |
| pub-a | `10.0.0.0/24` | 251 | a | ALB ENI · NAT GW |
| pub-c | `10.0.1.0/24` | 251 | c | ALB ENI · NAT GW |
| web-a | `10.0.10.0/24` | 251 | a | Apache EC2 |
| web-c | `10.0.11.0/24` | 251 | c | Apache EC2 |
| was-a | `10.0.20.0/24` | 251 | a | Tomcat EC2 · Internal ALB ENI |
| was-c | `10.0.21.0/24` | 251 | c | Tomcat EC2 · Internal ALB ENI |
| db-a | `10.0.30.0/24` | 251 | a | RDS 프라이머리 |
| db-c | `10.0.31.0/24` | 251 | c | RDS 스탠바이 |
| 예약 | `10.0.40.0/20` 이상 | — | — | 티어 확장 · 3번째 AZ(`-d`) 증설용 |

| ID | 규칙 |
| --- | --- |
| C-01 | 서브넷은 **/24 고정**. 크기를 제각각 잡으면 대역이 파편화된다. IP가 부족하면 /24를 하나 더 추가한다. |
| C-02 | 티어별 **3번째 옥텟 10단위 구획**(0=pub, 10=web, 20=was, 30=db)을 지킨다. 플로우 로그에서 IP만 보고 티어를 알 수 있다. |
| C-03 | 각 서브넷의 앞 4개와 마지막 1개 IP는 **AWS 예약**이다. /24의 실제 가용 IP는 251개. |
| C-04 | Public 서브넷은 **퍼블릭 IP 자동 할당을 끈다.** ALB와 NAT GW는 자체 ENI·EIP를 쓰므로 필요 없고, 켜두면 실수로 EC2를 만들었을 때 인터넷에 그대로 노출된다. |
| C-05 | 향후 다른 VPC와 연결할 가능성에 대비해 **`10.0.0.0/16`을 다른 팀·다른 실습과 겹치게 쓰지 않는다.** 겹친 채로 굳으면 피어링이 영구 불가능해진다. |

### 6.2 라우팅 정책

| 라우트 테이블 | 연결 서브넷 | `0.0.0.0/0` → | 추가 경로 |
| --- | --- | --- | --- |
| `ptc-rtb-pub` | pub-a, pub-c | `ptc-igw` | — |
| `ptc-rtb-web-a` | web-a | `ptc-ngw-a` | S3 prefix list → `ptc-vpce-s3` |
| `ptc-rtb-web-c` | web-c | `ptc-ngw-c` | S3 prefix list → `ptc-vpce-s3` |
| `ptc-rtb-was-a` | was-a | `ptc-ngw-a` | S3 prefix list → `ptc-vpce-s3` |
| `ptc-rtb-was-c` | was-c | `ptc-ngw-c` | S3 prefix list → `ptc-vpce-s3` |
| `ptc-rtb-db` | db-a, db-c | **없음** | 로컬 경로만 — DB는 인터넷 아웃바운드 전면 차단 |

> **AZ별 NAT의 전제 조건**
> NAT를 AZ마다 두기로 했으므로(D6), **라우트 테이블도 AZ별로 쪼개져 있어야** 의미가 있다. web-a와 web-c가 같은 라우트 테이블을 공유하면 두 AZ의 트래픽이 NAT 하나로만 흘러 이중화 비용이 그대로 낭비된다. `rtb-web-a`/`rtb-web-c`를 반드시 분리할 것 — 위 표에서 테이블이 6개인 이유다.

S3 Gateway Endpoint(`ptc-vpce-s3`)를 web·was·db 라우트 테이블에 **모두 연결**하면 war/이미지 다운로드 트래픽이 NAT를 우회한다. Gateway 엔드포인트는 요금이 없으므로 NAT 데이터 처리 비용을 줄이는 가장 확실한 수단이다 (§13.2).

## §7. 보안 그룹 체인

보안 그룹은 CIDR이 아니라 **다른 보안 그룹을 소스로 참조**한다. 인스턴스가 늘거나 IP가 바뀌어도 규칙을 고칠 일이 없고, 규칙 목록 자체가 아키텍처 문서가 된다.

| 보안 그룹 | 인바운드 소스 | 포트 | 아웃바운드 대상 | 비고 |
| --- | --- | --- | --- | --- |
| `ptc-sg-alb-ext` | `0.0.0.0/0` (HTTPS 구성 후 CloudFront prefix list로 축소 검토) | 80, 443 | `ptc-sg-web:80` | 유일하게 인터넷 인바운드가 허용되는 SG |
| `ptc-sg-web` | `ptc-sg-alb-ext` | 80 | `ptc-sg-alb-int:80` · 443 | 443은 S3·SSM 엔드포인트 통신용 |
| `ptc-sg-alb-int` | `ptc-sg-web` | 80 | `ptc-sg-was:8080` | WEB에서만 접근 — 외부 ALB는 여기 닿을 수 없다 |
| `ptc-sg-was` | `ptc-sg-alb-int` | 8080 | `ptc-sg-db:3306` · 443 | Tomcat 8080. AJP 8009는 열지 않음 (mod_proxy_http 채택) |
| `ptc-sg-db` | `ptc-sg-was` | 3306 | **없음** | WEB에서 직접 접근 불가 — 티어 건너뛰기 금지 |
| `ptc-sg-vpce` | `ptc-sg-web`, `ptc-sg-was` | 443 | — | SSM Interface 엔드포인트를 쓸 경우 |

| ID | 규칙 |
| --- | --- |
| S-01 | **22번 포트 인바운드는 어떤 SG에도 열지 않는다.** 접속은 SSM Session Manager로만 한다 (§8.4). 다이어그램의 "관리자 접속 · Bastion 대체" 경로가 이것이다. |
| S-02 | 인바운드 `0.0.0.0/0`은 **외부 ALB의 80·443**에서만 허용된다. 다른 SG에 나타나면 즉시 위반이다. |
| S-03 | 티어를 **건너뛰는 규칙 금지**. WEB→DB, 외부 ALB→WAS 같은 경로는 디버깅 편의상 열고 싶어져도 허용하지 않는다. 한 번 열면 계층 분리의 의미가 사라진다. |
| S-04 | 콘솔 기본값인 **아웃바운드 전체 허용을 그대로 두지 않는다.** 필요한 대상만 남기고, 특히 DB SG는 아웃바운드를 비운다. |
| S-05 | 모든 규칙에 **설명(Description)을 필수 기입**한다. 형식: `from <소스> for <목적>`. 설명 없는 규칙은 아무도 지우지 못해 영원히 남는다 — 전원이 편집 권한을 가진 지금 환경에서 특히 중요하다. |
| S-06 | SG 이름은 **생성 후 변경할 수 없다.** 만들기 전에 §3.5를 확인한다. |
| S-07 | 디버깅용으로 임시로 연 규칙은 **그날 안에 닫는다.** 닫을 때까지 그 사실을 팀 채널에 남긴다. |

## §8. IAM·접근 정책

팀장이 IAM 사용자를 발급하고 팀원 전원이 동일한 권한을 갖는 구조다(D2·D7). 권한으로 실수를 막을 수 없으므로, 이 절의 목적은 **권한 분리가 아니라 추적과 복구 가능성**이다.

### 8.1 사람 계정 원칙

| ID | 규칙 |
| --- | --- |
| I-01 | **루트 계정은 봉인한다.** MFA를 걸고, 계정 설정 변경처럼 루트로만 가능한 작업 외에는 로그인하지 않는다. 루트 액세스 키는 발급하지 않는다. |
| I-02 | **1인 1 IAM 사용자.** 계정 공유·비밀번호 공유 금지. CloudTrail 기록이 "누가"를 가리키지 못하면 이 구조의 유일한 안전장치가 사라진다. |
| I-03 | 모든 IAM 사용자에 **MFA 필수**. 권한이 큰 만큼 자격증명 유출의 파급이 크다. |
| I-04 | 권한은 사용자에게 직접 붙이지 않고 **그룹(`ptc-grp-builder`)에 부여**한다. 팀원 추가·제거가 그룹 멤버십 변경 한 번으로 끝난다. |
| I-05 | 액세스 키는 **필요할 때만 발급하고 과제 종료 시 즉시 삭제**한다. 발급받은 키를 Git에 커밋하지 않는다 — 공개 리포에 올라가면 수분 내 도용된다. |
| I-06 | 팀장은 **결제·IAM·루트 관련 작업을 전담**한다. 팀원 그룹에는 `iam:*`, `organizations:*`, 결제 콘솔 접근을 주지 않는 것이 바람직하다 (§15-Q2). |

### 8.2 EC2 역할

| 역할 | 부여 권한 | 사용처 |
| --- | --- | --- |
| `ptc-role-ec2-web` | AmazonSSMManagedInstanceCore · assets 버킷 **읽기 전용** · `/ptc/web/*` 파라미터 읽기 · CloudWatch Agent 쓰기 | Apache 인스턴스 프로파일 |
| `ptc-role-ec2-was` | SSM Core · assets 버킷(war) 읽기 · Secrets Manager `ptc/rds/*` 읽기 · CW Agent 쓰기 | Tomcat 인스턴스 프로파일 |

**EC2에 장기 액세스 키를 심지 않는다.** 인스턴스 프로파일만 사용하며, 인스턴스 안에 `~/.aws/credentials`가 있으면 그 자체가 위반이다. WEB 역할이 읽기 전용인 이유는, Apache가 침해당했을 때 CloudFront가 배포 중인 자산과 war 파일을 공격자가 교체하지 못하게 하기 위해서다. 다운로드만 하는 주체에는 `s3:GetObject`만 준다.

### 8.3 전원 동일 권한에서의 방어선

> **권한으로 막을 수 없다면 되돌릴 수 있게 만든다**
> 누구나 RDS를 지우고 SG를 열 수 있는 구조다. 다음 네 가지를 **구축 첫날에** 걸어둔다.
> 1. **RDS 삭제 방지** — 삭제 방지(deletion protection) 활성화, 최종 스냅샷 생성 유지. 실수 한 번이 DB 전체를 날리는 걸 막는다.
> 2. **CloudTrail 상시 기록** — 전 리전 추적을 켜고 로그를 `ptc-apne2-logs-…` 버킷에 보관. 누가 무엇을 지웠는지 확인할 유일한 수단이다.
> 3. **S3 버전 관리** — assets 버킷에 켜두면 덮어쓰기·삭제를 되돌릴 수 있다.
> 4. **소유 표시** — `Part`·`Owner` 태그(§5.1). 남의 파트 리소스는 담당자 동의 없이 수정·삭제하지 않는다는 것이 팀 규칙이며, 태그가 없으면 이 규칙이 작동하지 않는다.

### 8.4 운영 접근 (Bastion 대체)

다이어그램에 Bastion 호스트가 없고 SSM Session Manager로 표기된 것은 의도된 설계다. Bastion을 두면 그 자체가 패치·키 관리 대상이 되고, public 서브넷에 상시 노출된 SSH 포트가 생긴다.

- WEB·WAS는 **private 서브넷 · SSH 포트 미개방** 상태를 유지한다.
- 접속은 콘솔의 **Session Manager 탭** 또는 `aws ssm start-session --target i-xxxx`로만 한다.
- 세션 로그를 `/ptc/ops/ssm-session` 로그 그룹에 기록해 **누가 어떤 명령을 실행했는지** 남긴다.
- SSM은 아웃바운드 443이 필요하다 — NAT 경유로 동작하며, NAT 비용을 줄이려면 `ssm` · `ssmmessages` · `ec2messages` Interface 엔드포인트 3종을 만드는 방법도 있다 (단, 엔드포인트도 시간당 과금 — §13.2).

## §9. 도메인·HTTPS 구성

도메인 구매와 HTTPS 적용이 예정되어 있다(D4). 순서를 잘못 잡으면 인증서 검증에서 막히므로 단계를 고정한다.

### 9.1 구성 순서

1. **도메인 구매** — Route 53에서 직접 등록하면 호스티드 존과 네임서버가 자동 연결되어 가장 단순하다. 외부 등록기관을 쓰면 NS 레코드를 수동으로 옮겨야 한다.
2. **호스티드 존 확인** — 구매 도메인명으로 퍼블릭 호스티드 존이 생성되었는지 확인한다.
3. **ACM 인증서 2장 발급** — 서울(외부 ALB용), 버지니아 us-east-1(CloudFront용). 같은 도메인이라도 **리전별로 따로 발급**해야 한다.
4. **DNS 검증** — ACM이 제시한 CNAME을 호스티드 존에 추가. Route 53을 쓰면 콘솔에서 "레코드 생성" 버튼 한 번으로 끝난다.
5. **ALB 리스너 구성** — 443 HTTPS 리스너에 인증서 연결, 80 리스너는 443으로 **301 리다이렉트**.
6. **A 레코드(별칭) 연결** — 도메인 → 외부 ALB, `assets` 서브도메인 → CloudFront.

### 9.2 레코드 계획

| 레코드 | 타입 | 대상 | 비고 |
| --- | --- | --- | --- |
| `example.com` | A (별칭) | `ptc-alb-ext` | 서비스 진입점 |
| `www` | A (별칭) | `ptc-alb-ext` | 또는 루트로 리다이렉트 |
| `assets` | A (별칭) | `ptc-cf-assets` | 이미지 등 정적 자산 |

> **도메인 구매 전까지**
> ALB의 기본 DNS 이름(`ptc-alb-ext-xxxx.ap-northeast-2.elb.amazonaws.com`)으로 접속해 검증한다. 이 이름에는 **HTTPS를 붙일 수 없다** — ACM 인증서는 소유한 도메인에만 발급되기 때문이다. 따라서 HTTPS 검증 작업은 도메인 확보 이후로 미루고, 그전까지는 80 리스너로 기능 검증을 끝내둔다. 리다이렉트 설정은 마지막에 추가하면 된다.

**비용 참고:** 호스티드 존은 월 $0.50, 도메인 등록비는 TLD에 따라 연 $12 내외(`.com` 기준)다. ACM 인증서는 ALB·CloudFront에 붙이는 용도로는 무료다.

## §10. 데이터·암호화 정책

### 10.1 암호화 기준

| 대상 | 저장 시 | 전송 중 | 비고 |
| --- | --- | --- | --- |
| RDS | KMS (`alias/ptc-rds`) | TLS 권장 | **생성 후에는 암호화를 켤 수 없다** — 반드시 처음부터 켠다 |
| EBS | KMS | — | EC2 대시보드에서 **계정 기본 암호화를 먼저 켜두면** 누락이 없다 |
| S3 | SSE-S3 이상 · 버킷 키 ON | HTTPS 강제 | 버킷 정책에 `aws:SecureTransport=false` Deny |
| 사용자 ↔ CloudFront/ALB | — | TLS 1.2 이상 | §9 구성 후 · HTTP는 301 리다이렉트 |
| ALB ↔ WEB ↔ WAS | — | HTTP 허용 | VPC 내부 구간 · TLS는 ALB에서 종료 |
| CloudWatch Logs | 기본 암호화 | — | 민감 로그는 KMS 지정 |

### 10.2 비밀 관리

| ID | 규칙 |
| --- | --- |
| K-01 | DB 자격증명은 **Secrets Manager**(`ptc/rds/app-user`)에만 둔다. `application.properties`·user-data·AMI·Git 저장소에 평문 저장 금지. **PetClinic 설정 파일에 DB 비밀번호를 적은 채 커밋하는 것이 가장 흔한 사고**다. |
| K-02 | 비밀이 아닌 설정값(Internal ALB DNS, 앱 버전)은 **SSM Parameter Store**의 `String` 타입에 둔다. Standard 파라미터는 무료지만 Secrets Manager는 건당 월 $0.40이므로, 비밀이 아닌 것을 거기 넣지 않는다. |
| K-03 | user-data 스크립트는 **콘솔에서 누구나 평문으로 볼 수 있다.** 비밀번호를 넣지 말고, 부팅 시 인스턴스 역할로 Secrets Manager를 조회하게 한다. |
| K-04 | 과제 종료 시 **발급한 모든 자격증명을 삭제**한다. |

### 10.3 S3 공개 차단

다이어그램의 `petclinic-assets` 버킷은 CloudFront 오리진이자 war 배포 아티팩트 저장소다. **퍼블릭 액세스 차단 4개 설정을 모두 켠 채로** CloudFront **OAC**(Origin Access Control)를 통해서만 읽히게 한다. "CloudFront를 붙이려면 버킷을 공개해야 한다"는 오해로 퍼블릭 버킷을 만들면 **war 파일까지 인터넷에 노출**된다 — 애플리케이션 설정과 소스가 그대로 들어 있는 파일이다.

> **보존 기간을 반드시 지정한다**
> CloudWatch 로그 그룹의 기본 보존은 **"만료 안 함"**이다. 지정하지 않으면 과제가 끝난 뒤에도 로그가 쌓인 채 저장 요금이 계속 나간다. 로그 그룹을 만든 직후 보존 기간을 설정하는 것을 체크리스트에 넣는다.

### 11.2 알람 네이밍과 필수 알람

```
sys - 대상 - 지표 - 조건        예) ptc-alb-ext-5xx-high
조건: high · low · unhealthy
```

| 알람 | 조건 | 탐지 대상 |
| --- | --- | --- |
| `ptc-alb-ext-5xx-high` | 5분간 5xx 비율 > 5% | **헬스체크가 못 잡는 맹점** — Apache는 살아있는데 ProxyPass·Internal ALB가 죽은 상태 |
| `ptc-tg-web-unhealthy` | 정상 호스트 < 2 | WEB 인스턴스 이탈 |
| `ptc-tg-was-unhealthy` | 정상 호스트 < 2 | WAS 인스턴스 이탈 |
| `ptc-alb-ext-latency-high` | p95 > 2초 | WAS 응답 지연 · DB 병목 |
| `ptc-rds-cpu-high` | CPU > 80% (10분) | 쿼리 부하 |
| `ptc-rds-conn-high` | 커넥션 > 120 | DBCP 커넥션 누수 |
| `ptc-rds-storage-low` | 여유 < 20% | 디스크 고갈 |
| `ptc-ngw-errorport-high` | 포트 할당 오류 > 0 | NAT 포트 고갈 |
| `ptc-billing-cost-high` | §13.3 임계액 초과 | **예산 초과 조기 경보** |

### 11.3 헬스체크 역할 분리

외부 ALB는 **WEB(Apache)만 얕게** 확인하고(정적 `/health.html`), Internal ALB는 **WAS(Tomcat)만** 확인한다. 각 LB가 자기 바로 뒤 티어에만 책임을 진다.

> **딥 헬스체크를 금지하는 이유**
> 외부 ALB가 `/petclinic`까지 관통해 검사하면, WAS 한 대가 죽었을 때 **멀쩡한 WEB 인스턴스까지 unhealthy로 판정되어 서비스에서 빠진다.** 장애 하나가 두 티어를 동시에 무너뜨리는 구조가 된다. 연동 단절은 `ptc-alb-ext-5xx-high` 알람으로 잡는다.

## §14. 운영 거버넌스 (콘솔 수동 구축)

IaC가 없으므로 코드 리뷰도 `terraform plan`도 없다. **규칙을 지키게 하는 것은 전적으로 아래 절차**이며, 특히 전원이 동일 권한인 상황에서는 이 절이 가장 중요하다.

### 14.1 생성 전 규칙

| ID | 규칙 |
| --- | --- |
| G-01 | 리소스를 만들기 전에 **§3에서 표준명을 찾아 복사**한다. 표에 없으면 만들지 말고 §14.4를 먼저 따른다. |
| G-02 | 생성 화면에서 **태그를 그 자리에 입력**한다(§5.1 여섯 개). 나중에 몰아서 달면 반드시 빠진다. |
| G-03 | 공용 리소스(VPC·서브넷·SG·ALB·RDS)는 **담당자 1명만** 만든다. 두 사람이 동시에 만들면 중복 리소스가 생기고, 이름이 같으면 둘 중 하나는 실패한다. |
| G-04 | 생성 순서를 지킨다: **VPC → 서브넷 → IGW/NAT → 라우트 테이블 → SG → RDS → WAS → Internal ALB → WEB → 외부 ALB.** 뒤 단계가 앞 단계를 참조하므로 순서를 건너뛰면 되돌아가야 한다. |

> **Internal ALB와 WEB의 순서 의존성**
> WEB 인스턴스의 `ProxyPass`에는 Internal ALB의 DNS 이름이 필요하다. 따라서 **Internal ALB를 WEB보다 먼저** 만든다. 그 DNS 이름을 `/ptc/web/internal-lb-dns` 파라미터에 저장해두고 user-data가 부팅 시 읽어가게 하면, ALB를 재생성해 DNS가 바뀌어도 AMI나 스크립트를 고칠 필요가 없다.

### 14.2 생성 대장

콘솔 수동 구축에서 **재현과 인수인계의 유일한 근거**다. 공유 스프레드시트(또는 노션 데이터베이스)에 다음 열로 기록한다.

| 열 | 내용 |
| --- | --- |
| 표준명 | §3의 이름 |
| 리소스 ID | `vpc-0abc…` 실제 생성된 ID |
| 타입 · 리전 · AZ | — |
| 담당(Part) · 생성자 | 태그와 일치해야 한다 |
| 생성일 | — |
| 주요 설정값 | CIDR, 포트, 인스턴스 타입, 헬스체크 경로 등 기본값과 다르게 준 것 |
| 의존 리소스 | 삭제 순서 판단용 |

기본값과 다르게 설정한 화면은 **스크린샷을 남긴다.** 산출물 제출과 장애 복구 양쪽에 쓰인다.

### 14.3 변경·삭제 규칙

| ID | 규칙 |
| --- | --- |
| G-05 | **남의 파트 리소스는 담당자 동의 없이 수정·삭제하지 않는다.** 권한이 있다는 것과 해도 된다는 것은 다르다. |
| G-06 | SG 규칙·라우트 테이블처럼 **공유 리소스를 바꿀 때는 팀 채널에 먼저 알린다.** 남의 디버깅 중인 경로를 끊는 사고가 가장 흔하다. |
| G-07 | 삭제는 **의존 역순**으로 한다: 외부 ALB → WEB → Internal ALB → WAS → RDS → NAT/EIP → 서브넷 → VPC. |
| G-08 | 주 1회 **점검 시간**을 정해 태그 누락(Tag Editor), 미사용 리소스, 비용 추이를 함께 확인한다. |
| G-09 | 삭제 사고가 나면 **CloudTrail에서 이벤트를 찾아** 무엇이 지워졌는지 먼저 확정한다. 추측으로 복구하면 상태가 더 꼬인다. |

### 14.4 표준 확장과 예외

| ID | 규칙 |
| --- | --- |
| E-01 | §3에 없는 리소스는 **약어를 임의로 만들지 말고** 이 문서에 행을 추가한 뒤 만든다. 약어는 AWS 콘솔 표기를 따르고 3–8자로 한다. |
| E-02 | AWS 제약 때문에 규칙을 못 지키면 **예외를 문서에 기록**한다. 기록 없는 예외는 위반이다. |
| E-03 | 이미 만든 리소스의 이름이 규칙과 다를 때, **재생성 비용이 큰 것(RDS·SG·ALB)은 이름을 유지**하고 `Name` 태그로 보정한다. 이름을 맞추려고 RDS를 다시 만들지 않는다. |
| E-04 | 이 문서를 고치면 **리비전 번호를 올리고** 변경 사유를 남긴다. |

### 14.5 리소스 생성 체크리스트

- [ ] 이름이 §3 표준명과 글자 단위로 같은가
- [ ] 필수 태그 6종을 생성 화면에서 입력했는가
- [ ] ASG라면 "새 인스턴스에 태그 지정"을 켰는가
- [ ] SG라면 모든 규칙에 설명이 있고 `0.0.0.0/0`이 새로 생기지 않았는가
- [ ] 로그 그룹이라면 보존 기간을 지정했는가
- [ ] RDS라면 암호화 · 삭제 방지 · Multi-AZ를 켰는가 (생성 후엔 암호화를 못 켠다)
- [ ] 서브넷 CIDR이 §6.1 할당표와 일치하는가
- [ ] 생성 대장에 기록했는가
